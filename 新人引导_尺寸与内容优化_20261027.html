三、真根因：rpx 是按「屏宽」换算的

提词页 pageOrientation: "auto"，横屏是它的主场景。而 rpx 按屏宽折算：

  • 375px 竖屏 → 1rpx = 0.5px
  • 844px 横屏 → 1rpx ≈ 1.125px，所有尺寸放大 2.25 倍

与此同时可用高度只剩 390px。于是字号、内边距、行距一起涨、容器一起塌 —— 必然溢出。

上一轮（CONTEXT 第三十一节）的结论是错的

原文：「横屏下卡片必然高于视口，靠缩字号是做不到「不滚动」的 —— 正确解法是缩小 + 内容区可滚 + 按钮吸底」。

「必然」是假象。max-height: 84vh + body{overflow-y:auto} 只是把溢出藏起来（变成卡片内部滚动），用户依然看不到全部步骤，而且没有任何滚动提示。

四、改法：竖向尺寸改用 vmin（短边），宽度不用

vmin = 短边 / 100。竖屏时短边就是屏宽，所以 1rpx 恰好等于 0.13333vmin，观感与原来逐像素一致；横屏时短边变成屏高，尺寸不再随宽屏放大。

原值新值用在哪

26rpx3.47vmin步骤主标、卡片内边距
28rpx3.73vmin按钮字号
30rpx / 46rpx4vmin / 6.13vmin图标字号 / 图标列宽
34rpx4.53vmin标题

写法是同一属性写两行：rpx 先兜底，vmin 后覆盖。低版本 WebView 若不认 vmin，第一行仍生效，不会退化成默认值。

.tp-guide-title {
  font-size: 34rpx;      /* 兜底 */
  font-size: 4.53vmin;   /* 短边基准：横屏不再放大 */
}

但宽度没有跟着换。 卡片宽度改成 width: 84% + max-width: 600rpx / 80vmin（双写），高度上限 84vh → 88vh。若宽度也按短边算，横屏会缩成一条窄缝；若继续按 rpx 放大，横屏会变成 675px 的横条。当前这套组合让卡片宽度稳定在 288～330px，横竖屏一致。

一个反直觉的结果

七、顺带修掉两处视觉不统一

① ⏩ 是强制彩色 emoji，压根不跟随 color

U+23E9 的 Emoji_Presentation = Yes，在深色卡片上渲染成蓝色方块，而旁边的 ▶ ⚙ 是跟随色值变绿的文本符号 —— 同一列图标三种观感。换成 »（U+00BB，纯文本呈现）后统一为绿色。

判据：图标位只能用默认文本呈现的码位；带 Emoji_Presentation 的一律不用。（这条已写进测试的静态守卫。）

② 编辑页图标原来根本没写 color

.ed-guide-ico 缺 color，图标继承默认色 → ✎ 发白、▶ 发绿，同一张卡片两个图标不同色。补 color:#FFD166（本页强调色，与标题/按钮同色；图标体积小，不抢标题重心）。

测量器本身的三个坑（都已踩过并修好，别再退化）

  1. 不能用 --window-size：headless Chrome 会把浏览器外框算进去，请求 390 高实际只剩 303，比例全错。必须用 CDP 的 Emulation.setDeviceMetricsOverride。
  2. 必须 mobile: false：小程序的布局宽度 = 设备宽度；若开 mobile 模拟又缺 viewport meta，Chrome 会把布局宽度钉成 980px，量出来 981×1744 这种离谱数字。
  3. 不能靠 requestAnimationFrame 回写结果：--dump-dom 可能早于 rAF 执行，读到的永远是 pending。改成同步求值。
