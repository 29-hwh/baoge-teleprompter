二、查出的真缺陷：联合说话人被切碎

既然真实稿件里没有，就把「现实中必然出现」的写法逐条列出来测（末节 25 条）。查出一条：

✕ 修复前
输入：王建华、杨凤：我们一起回来了。

输出：「王建华、」
     「杨凤：我们一起回来了。」
一行两人齐声的台词被当成「杨凤单独说话」，前一行只剩半句残词。
✓ 修复后
输入：王建华、杨凤：我们一起回来了。

输出：「王建华、杨凤：我们一起回来了。」
整组保留为一行，不切、不丢字、不留残词。

根因：说话人左边界规则只要求「前一字符非中文」—— 用来防住「…也当晚处理掉：」这类正文被误切。 但顿号 、 与连接词 和 / 与 / 及 / 跟 / 同 恰好也满足「非中文」， 于是并列结构被误当成了切点。

三、修复：三轮迭代才收敛

第 1 轮
一律不切
残句没了。但漏切：…追剧还儿子、王建华：明天还得早起。（真粘连 + 联合）两行粘成一行 —— 被模糊测试 IM1 抓到。
第 2 轮
切点左移
把切点从「B：」左移到整组最前面。段首组移到 0 仍是一行；真粘连组移到「儿」前正好断开。但三人联合只移了一级。
第 3 轮
循环左移
王建华、杨凤、婆婆： 连移两级到位（上限 8 级防死循环）。规则收敛。

最终规则是三态，不是「切 / 不切」两态 —— 这是三轮迭代真正的收获：

切点左侧的情形语义处置例子
不是并列连接普通切点照旧切 杨凤：好。王建华：嗯。 → 2 行
是并列连接，且连接词左侧是白名单名字 联合说话人组 切点左移到组的最前面 王建华、杨凤：… → 1 行
杨凤：追剧还儿子、王建华：… → 2 行
是并列连接，且连接词左侧不是名字 正文里的并列标点 切点作废（整格不切） 杨凤：他买了菜、王建华：我不去。 → 1 行
第三态是关键。「他买了菜、王建华：」里的顿号属于正文（左侧是「了菜」，不是名字）， 这时切了才会留下「…了菜、」残句 —— 所以判定作废、保持一句完整。 判据只认「连接词左侧是不是本稿确实当过说话人的名字」，不做更复杂的句法推断。

已知差异（本轮刻意不动）

中文连接词在角色识别层会被整体当成一个角色名。 张阿姨和儿媳妇：… 会被识别成角色「张阿姨和儿媳妇」（因为全是汉字）， 而顿号形式的 王建华、杨凤：… 因含标点被判非法、回退取第一个名字。 这是 engine/role.js 的既有行为，属于角色识别层，与拆分器无关； 真实三部剧本实测 0 处这类写法，故本轮不处理 —— 已在 CONTEXT.md 第二十八节记录。

三个坑（写给未来的自己）

  • 联合行的名字进不了白名单。collectSpeakerNames 只认「行首 ≤5 字 + 冒号」， 而「王建华、杨凤：」不以「王建华：」起头 → 联合行自己贡献不了白名单。测试台里必须从 「已在物理行首露过面」的名字池里挑成员，否则「已进白名单也不许切开」这条守门断言形同虚设。
  • 诊断脚本的判定必须与产品同源。初版自己写了一套简化规则，把产品故意不切的两处 （引号内引用、联合说话人）误报成「粘连」。现已直接调用产品函数。
  • 先定位根因再动手。上一轮的教训（改文档反而改坏数据）在这一轮同样适用： 本轮全程只改小程序，文档 MD5 始终未变。
